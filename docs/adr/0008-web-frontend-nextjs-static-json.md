# ADR 0008: Web front end in Next.js (Vercel) rendering JSON exported by Python

- Status: **Proposed.** It becomes Accepted only when the owner approves this text. Nothing is
  uploaded to Vercel (preview or production) without the owner's explicit yes in the conversation.
- Date: 2026-11-23
- Scope: presentation only. No change to training, evaluation, priors, split, labels, thresholds,
  calibration, metrics, floors or verdict rules. ADR 0001 to 0007 are unchanged.
- Decision already taken by the owner (not reopened here): path A. A Next.js site on Vercel that only
  renders JSON exported by a Python script that reuses the existing dashboard functions. Streamlit
  stays as the local engine and app. Visual direction is monochrome. Data scope is aggregates and
  HEALPix regions only.

## 1. Context

The Streamlit dashboard (`src/astro_triage/dashboard/`, 70 modules, 8,778 lines for 5 pages) is
correct but, in the owner's words, ugly and disorganized. Two earlier rounds of restyling inside
Streamlit (`.claude/state/redesign-specs/00..09`, 2026-11-17/18) improved the content but not the
look. The evidence that the problem is structural, not cosmetic:

## 2. Decision

1. **Export, then render.** A new pure Python package `astro_triage.web_export` loads one release
   with the existing loaders and writes six JSON files (`meta`, `overview`, `sky`, `galaxies`,
   `compare`, `method`) to `web/data/<release>/`. It calls the existing pure functions
   (`data_headline`, `overview_model`, `overview_text`, `sky_model`, `data_sky`, `sky_text`,
   `data_galaxy_prior`, `compare_model`, `compare_text`, `verdict_rule`, `data_dl`, `method_notes`,
   `html_method` constants, `limits_pt`). It never imports `streamlit`, `data_cached` or any `views_*`.
2. **Python owns every number and every data-dependent sentence; TypeScript owns layout.** Each
   displayed number ships as a raw value plus its pt-BR text produced by `fmt.*`. Every sentence that
   contains a number or branches on data ships as text. TypeScript holds only static labels with no
   digits. No HTML ever crosses the boundary (plain strings only).
3. **Static site.** Next.js App Router with `output: "export"`; the JSON is read at build time from
   `web/data/<ASTRO_RELEASE>/`. One deployment shows one release. No server, no API, no runtime
   data fetch.
4. **No data in git.** `web/data/`, `web/out/`, `web/.next/` and `web/.vercel/` are git-ignored.
   Vercel is deployed with the CLI from a prebuilt local build, never from a Git integration (a Git
   build would have no data). Only synthetic fixtures generated by the test suite are versioned.
5. **n/a is `null`, never `0`.** A metric below the reporting floor, absent, or not finite is `null`
   with text `"n/a"`. JSON is written with `allow_nan=False`.
6. **Always provisional.** Every file carries `provisional: true`. The exporter has no switch to
   emit `false`; changing that needs a new ADR (CLAUDE.md, "Status").
7. **Streamlit stays** as the local engine and app. It is not restyled further and not deleted.
8. **Visual direction.** Monochrome tokens (black, graphite, greys, white). Series are told apart by
   marker shape, stroke pattern and direct labels, never by hue. Local fonts Instrument Serif and
   Inter (the files already in `dashboard/static/fonts/`). Minimum 15 px secondary text, 44 px
   targets, text contrast >= 4.5:1, graphic contrast >= 3:1 (same floors as `theme.py:24-32`).
9. **UI state in the URL.** `?regra=<as_shipped|prior_matched>&prior=<P1|P2|P3>&tecnico=<0|1>`. The
   allowed (rule, prior) pairs and the default come from `meta.json`; an unknown pair falls back to
   the default. No normalization logic in TypeScript beyond that lookup.

## 3. Alternatives rejected

| Option | Real cost | Why rejected |
|---|---|---|
| Streamlit + more CSS | Low effort; keeps one stack | Already tried twice (specs 00..09); styling rests on internal `data-testid` selectors (P1); still needs the per-object data at run time, so it cannot go to Vercel (P11) |
| Embed Streamlit in an iframe | One Next shell plus a public Streamlit server | Needs a hosted Python server holding raw data (paid or exposed); double navigation and scroll; the ugly page is still the content |
| Separate API (FastAPI or similar) serving JSON live | A hosted Python service, state, uptime, CORS | Data changes once per release, so live serving buys nothing; hosting means per-object data on a server and a paid provider, which needs its own ADR |
| TypeScript reimplementing the logic | No exporter; one stack on the web side | Two copies of the verdict rule (`verdict_rule.py` exists so there is one), Wilson intervals, floors and n/a rules; silent drift; breaks "no number typed by hand" |

## 4. Consequences

Good: the web front end is a leaf (nothing in Python imports it; deleting `web/` and
`web_export/` removes it). Numbers keep one source. The site can be hosted without raw data. The
layout is free of Streamlit internals.

Bad, accepted:
- A Node toolchain enters a Python repository (Next.js, React, TypeScript, a test runner, a linter).
  New dependencies trigger the `security` gate.
- The JSON schema lives in two languages (Python writer, TypeScript types). Any change bumps
  `schema_version` and both sides.
- The deploy needs a machine with `data/` (the owner's). CI can only build against fixtures.
- No release selector on the web: one deployment per release. Older releases stay reachable only
  through their own immutable deployment URLs.
- Two front ends exist. Layout drift between them is accepted; number drift is not (section 6).
- About ten small extractions in the dashboard (task W1) move logic out of views so the exporter can
  call it. Streamlit output must not change.

Maintenance cost: about 6 Python files plus tests on the export side, about 35 TypeScript files on
the web side, one CI job, and a dependency update every few months.

## 6. Parity plan

1. **Field-level parity test** (`tests/test_web_export_parity.py`). Build a synthetic release (same
   pattern as `tests/test_dashboard_galaxy_prior.py::fake_release`), run the exporter into
   `tmp_path`, and for each page compare every exported value with the direct output of the
   function that produces it (e.g. `overview.rows[i].purity.point ==
   overview_model.build(...).rows[i].purity.point`; `compare.grid[k].state ==
   compare_model.build(results).grid[k].state.value`). Equality is exact: JSON floats from Python
   round-trip.
2. **Real-release parity**, same assertions, skipped when `ASTRO_DATA_ROOT` has no
   `interim/<release>/eval/results.json` (pattern of `tests/test_dashboard_overview_v3.py:141-144`).
3. **Invariants**: n/a cells are `null` (never `0`) wherever the source is below the floor or not
   `status == "ok"`; no NaN or Infinity; `provisional` is `true`; no string contains `<` or "ADR";
   forbidden keys absent; size budgets met.
4. **Formatting parity**: the exporter writes `fmt_samples.json` (inputs and `fmt.pt_*` outputs);
   the web test asserts that `web/lib/fmt.ts` (used only for axis ticks) gives the same strings.
5. **Render parity** (web): every page renders from the fixture export; every text node with a digit
   must equal a `text` field of the JSON or a tick produced by `fmt.ts`.
6. **Fixture drift guard**: the Python suite regenerates `web/test/fixtures/` from the synthetic
   release and fails if it differs from the versioned copy.

## 7. Reversal trigger

Revert (delete `web/` and `astro_triage/web_export/`; Streamlit is untouched) if any of these holds:
the parity test needs a tolerance or an exception list to pass; the owner wants interactive
recomputation (arbitrary threshold or prior) that cannot be pre-exported in under 1 MB; the licence
review forbids publishing the aggregates; Vercel requires a paid plan for this use (a paid provider
needs a new ADR).

## 8. Non-goals

Restyling Streamlit; deleting dead `charts_*` modules; a release selector on the web; per-object views
(scatter, cut-outs, `source_id`); Layer 2 (closed, ADR 0005); any recomputation, new metric or test
read; analytics, cookies, login; a custom domain; rebuilding the graph.

## Appendix A. JSON schema (version 1)

Common types:

```text
Num   = { value: number | null, text: string }                 # text "n/a" when value is null
Est   = { point: number | null, lo: number | null, hi: number | null,
          text: string, ci_text: string }                       # all null + "n/a" below the floor
Rule  = "as_shipped" | "prior_matched"
Prior = "P1" | "P2" | "P3"
Head  = { schema_version: 1, release: string, provisional: true, generated_at: string(ISO 8601),
          page: string }                                        # first keys of every file
```

`meta.json`: `Head` + `states: [{rule, prior, label}]` (the 4 rows of `overview_model.ROW_ORDER`),
`default_state` (`ui_state.DEFAULT`), `shipped_prior` ("P2"), `partial_priors` (["P3"]),
`rule_labels` (`ui_state.RULE_LABEL`), `seal_text`, `nside` (`data_sky.HEALPIX_NSIDE`),
`band_edges_deg` (`data_sky.BAND_EDGES_DEG`), `floor: {min_objects, min_pixels}` (`rel.meta.floor`),
`n_boot`.

`overview.json` (sources: `data_headline.shipped_state`, `prior_states`, `accuracy_defs`,
`overview_model.build`, `overview_text.answer`, `html_overview.partial_note`; technical:
`data_overview_page.load_page`, `data.metrics_frame`, `paired_diffs_frame`, `model_summary`,
`feature_importance`, `confidence_histogram`, `calibration_points`):
- `rows[4]`: `{rule, prior, partial: bool, qso_prior: Num, purity: Est, completeness: Est,
  accuracy: Num, answer_text, partial_notice: string | null}`. `accuracy` is `null` under
  `prior_matched` (decision D1, spec 03 D-04). P3 rows have `partial: true` and a `partial_notice`.
- `accuracy_note`.
- `technical`: `data_box {n_pairs, n_test, n_errors, n_pixels, accuracy, qso_hits, qso_total: Num;
  class_mix {STAR, GALAXY, QSO}: Num}`, `validation: {purity, completeness: Num} | null`,
